# KV260 PYNQ package

This directory is self-contained. Copy the entire directory to the KV260 and
run:

```bash
cd PYNQ
python3 pynq.py
```

The `pynq.py` compatibility entry point loads `KV260.bit` and `KV260.hwh`, initializes the packaged SDF and
triangle data, streams 180 default 1920x1080 frames, builds the normal
G-buffer with OpenMP, shades it with the Mali fragment shader, and continuously
sends the result to HDMI/DisplayPort through direct EGLImage/DRM scanout. The
default DMA batch capacity is 2,097,151 rays, so a 1920x1080 frame uses one
batch. `mem/pynq_render_data.bin` is the PS-side render
sidecar generated by `make sim`; it must match the deployed
`mem/triangle_ddr.bin`. Hit processing uses one OpenMP thread by default;
tune `--render-threads` for the board workload.

The board must have PYNQ installed with `pynq`, NumPy, and Pillow available,
and the CMA pool must provide buffers inside the DMA DDR windows exported in
`KV260.hwh`.  The current hardware maps both `ray_dma` and `tri_datamover`
through PS HP0 low DDR (`0x00000000..0x7fffffff`), so buffers allocated above
that range cannot be reached by PL DMA and the script will stop before running.
Use `--readback-display --width 320 --height 180`, or set
`KV260_RT_DIRECT_SCANOUT=0` through the board wrapper, for a smaller smoke
test. Direct scanout uses the connected 1024x768 DRM mode and therefore
requires a render surface at least that large.

## Runtime layout

The implementation follows a package layout so hardware access, rendering,
and orchestration can evolve independently:

```text
pynq.py                 compatibility entry point
sdf_rt/config.py        RTL addresses, DMA registers, and defaults
sdf_rt/formats.py       FP9/memory parsers and AXI stream codecs
sdf_rt/camera.py        orbit-camera rays and tiled raster order
sdf_rt/shading.py       camera and triangle tables used by G-buffer generation
sdf_rt/mali.py          OpenMP/Mali bridge and frame lifecycle
native/                 AArch64 OpenMP G-buffer and Mali fragment shader
sdf_rt/dma.py           Overlay, MMIO, CMA buffers, SDF setup, and AXI DMA
sdf_rt/pipeline.py      ray-update/Trace/G-buffer/BRDF pipeline
sdf_rt/io.py            ray prepacking and image/result output
sdf_rt/app.py           full-frame lifecycle and performance stats
sdf_rt/cli.py           command-line parser and validation
```

Deploy the complete `PYNQ/` directory. Copying `pynq.py` without `sdf_rt/`
is not sufficient.

## SDF memory layout

The logical hierarchy is global `16x16x16`, local `8x8x8`, with at most 2048
global cells mapped to local blocks. The deployed physical memories are kept
unchanged: global is 4096 rows by 72 bits, local is 16384 rows by 576 bits,
and mapping is 16384 32-bit words packed into the existing 128-bit BRAM rows.
Global rows 0..511 and mapping words 0..2047 are active; their physical tails
are zero-filled. Each local block occupies eight consecutive rows:
`row = cell_id * 8 + local_z`, `lane = local_x + local_y * 8`.

## Mali BRDF path

OpenMP C++ decodes FPGA `hitId/hitT/u16/v16` records and converts the hardware
barycentric coordinates directly into an RGBA8 oct-normal G-buffer. Result
decode and normal generation share one parallel pass. Every frame traces and
builds the complete lossless raster; only the first and final frames retain
full-frame hit results. An OpenGL ES 2.0 fragment shader then performs environment and BRDF
shading. Build it on the KV260 with `make -C native`; host-built shared objects
cannot be deployed to the AArch64 board:

```bash
make -C native clean all
python3 pynq.py --render-threads 1 --width 320 --height 180
```

The production path trusts the hardware RayID permutation and avoids allocating
and clearing a per-frame duplicate-ID table. Use `--validate-result-stream`, or
set `KV260_RT_VALIDATE_RESULT_STREAM=1` through the board wrapper, when debugging
stream ordering or corruption.

Mali uses an offscreen EGL surface and opens no window. HDMI/DisplayPort is the
only display output path.

Continuous rendering uses an asynchronous four-stage pipeline. A `ray-update`
worker generates the next orbit-camera frame into two reusable CMA buffers, the
main thread owns FPGA Trace/DMA, one worker owns the OpenMP normal G-buffer
stage, and one worker owns the Mali EGL context and BRDF stage. Three independent
frame contexts prevent adjacent stages from writing the same G-buffer or RGB
image.

The camera completes one 360-degree orbit every 180 frames by default. Every
frame updates and traces all pixels without a hit-derived ROI. Set
`KV260_RT_ROTATION_PERIOD_FRAMES=N` through the board wrapper or pass
`--rotation-period-frames N`; use `0` to keep the static camera. The generated
ray directions and Mali camera uniforms are frame-local so ray generation can
overlap the other stages without changing an in-flight frame.

HDMI/DisplayPort uses synchronized front/back frames. BRDF publishes only a
complete RGB frame, and the display thread swaps it at the next `writeframe`
boundary. A producer waits until the previous frame has been submitted, so
partially rendered frames and silent frame drops are not displayed.

For display diagnostics, `--save-ppm PATH` saves the final Mali readback before
HDMI publication and also writes `PATH.gbuffer.ppm`. The log includes min/max,
nonzero-channel count, and CRC32 values. Through the board wrapper, set
`KV260_RT_SAVE_PPM=/home/ubuntu/kv260_rt/verification/frame.ppm`.

Zero-copy Direct scanout is the default. Mali renders into double-buffered
EGLImage/DRM buffers at the connected `1024x768` mode, and the native backend
waits for the vblank boundary before reusing a buffer. Use
`KV260_RT_DIRECT_SCANOUT=0` through the board wrapper, or pass
`--readback-display` directly, to select the diagnostic GPU-readback path. Use
`KV260_RT_SCANOUT_PPM=/home/ubuntu/kv260_rt/verification/scanout.ppm` for a
diagnostic dump; this is mutually exclusive with `KV260_RT_SAVE_PPM`.
