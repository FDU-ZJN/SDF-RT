# KV260 PYNQ package

This directory is self-contained. Copy the entire directory to the KV260 and
run:

```bash
cd PYNQ
python3 pynq.py
```

The `pynq.py` compatibility entry point loads `KV260.bit` and `KV260.hwh`, initializes the packaged SDF and
triangle data, streams 180 default 1920x1080 frames, builds compact hit data
with OpenMP, shades it with the Mali fragment shader, and continuously
sends the result to HDMI/DisplayPort through direct EGLImage/DRM scanout. The
default David workload traces the orbit-union ROI
`x=732,y=252,width=456,height=604` (275,424 rays). Use `--full-frame` for the
2,073,600-ray regression path or `--trace-roi X Y WIDTH HEIGHT` for another
4x4-aligned region. The default DMA batch capacity is 2,097,151 rays, so either path uses one
batch. `mem/pynq_render_data.bin` is the PS-side render
sidecar generated by `make sim`; it must match the deployed
`mem/triangle_ddr.bin`. `mem/sdf_uram.bin` is the versioned, CRC-protected FP9
image written by the PS through the SDF loader aperture. Hit processing uses four OpenMP threads by default;
tune `--render-threads` for the board workload.

The board must have PYNQ installed with `pynq` and NumPy available,
and the CMA pool must provide buffers inside the DMA DDR windows exported in
`KV260.hwh`.  The current hardware maps both `ray_dma` and `tri_datamover`
through PS HP0 low DDR (`0x00000000..0x7fffffff`), so buffers allocated above
that range cannot be reached by PL DMA and the script will stop before running.
Direct scanout is the only display backend. A smaller smoke test must set both
the render and scanout dimensions, for example `--width 320 --height 180
--display-width 320 --display-height 180`.

## Runtime layout

The implementation follows a package layout so hardware access, rendering,
and orchestration can evolve independently:

```text
pynq.py                 compatibility entry point
sdf_rt/config.py        RTL addresses, DMA registers, and defaults
sdf_rt/formats.py       FP9/memory parsers and AXI stream codecs
sdf_rt/camera.py        orbit-camera rays and tiled raster order
sdf_rt/render_data.py   camera, normal, and compact-ID tables for G-buffer generation
sdf_rt/mali.py          OpenMP/Mali bridge and frame lifecycle
native/                 AArch64 OpenMP G-buffer and Mali fragment shader
sdf_rt/dma.py           Overlay, MMIO, CMA buffers, SDF setup, and AXI DMA
sdf_rt/pipeline.py      Trace/G-buffer/BRDF pipeline
sdf_rt/io.py            one-time static ray prepacking
sdf_rt/app.py           full-frame lifecycle and performance stats
sdf_rt/cli.py           command-line parser and validation
```

Deploy the complete `PYNQ/` directory. Copying `pynq.py` without `sdf_rt/`
is not sufficient.

## SDF memory layout

The logical hierarchy is global `16x16x16`, local `8x8x8`, with at most 2048
global cells mapped to local blocks. The PS loads all three regions from the
single `sdf_uram.bin` runtime image; they are not initialized in the bitstream.
The deployed physical memories are unchanged: global is 4096 rows by 72 bits,
local is 16384 rows by 576 bits, and mapping is 16384 32-bit words packed into
the existing 128-bit BRAM rows.
Global rows 0..511 and mapping words 0..2047 are active; their physical tails
are zero-filled. Each local block occupies eight consecutive rows:
`row = cell_id * 8 + local_z`, `lane = local_x + local_y * 8`.

## Mali BRDF path

OpenMP C++ decodes FPGA `hitId/hitT/u16/v16` records and writes one RGBA8
record per hit containing the source triangle ID and 8-bit U/V coordinates.
Vertex normals are oct-encoded once in a persistent Mali texture atlas. The
OpenGL ES 2.0 fragment shader fetches the three vertex normals, interpolates
and orients them, then performs environment and BRDF shading. Misses sample a
static background texture captured during scanout initialization, so pixels
outside the ROI are initialized correctly and old silhouettes do not remain
in the double buffers. Every frame
traces and builds the configured lossless ROI; only the first and final frames
retain full-frame hit results. Build the native path on the KV260 with
`make -C native`; host-built shared objects cannot be deployed to the AArch64
board:

```bash
make -C native clean all
python3 pynq.py --render-threads 4 --width 320 --height 180 \
  --display-width 320 --display-height 180
```

The production path trusts the hardware RayID permutation and avoids allocating
and clearing a per-frame duplicate-ID table. Use `--validate-result-stream`, or
set `KV260_RT_VALIDATE_RESULT_STREAM=1` through the board wrapper, when debugging
stream ordering or corruption.

Mali uses an offscreen EGL surface and opens no window. HDMI/DisplayPort is the
only display output path.

Continuous rendering reuses one prepacked CMA ray buffer. The PS commits a
frame-wide camera origin and Y-axis sin/cos at MMIO word `0xFFC40`; InitStage
rotates each original direction before AABB/SDF traversal. The main thread owns
FPGA Trace/DMA, one worker owns the OpenMP normal G-buffer stage, and one worker
owns the Mali EGL context, BRDF stage, and DRM page flip.
Three independent frame contexts prevent adjacent stages from writing the same
G-buffer.

The camera completes one 360-degree orbit every 180 frames by default. Every
frame reuses the fixed ROI ray buffer while hardware rotates the camera. Set
`KV260_RT_ROTATION_PERIOD_FRAMES=N` through the board wrapper or pass
`--rotation-period-frames N`; use `0` to keep the static camera. The generated
transform parameters are committed only between hardware batches. The Mali
shader orients decoded normals against its reconstructed ray direction, so the
CPU G-buffer does not read or rotate per-hit directions.

HDMI/DisplayPort uses front/back EGLImage/DRM overlay buffers. Mali completes
rendering before the active plane is changed; the display controller latches
the plane update on scanout. The rendered dirty ROI is also converted into the
RGB888 primary framebuffer required by the deployed KV260 display path. The
runtime has no image readback or frame file output path.

Mali renders into double-buffered EGLImage/DRM buffers at the connected
`1024x768` mode. Console performance, result validation, and hardware error
status remain available without writing runtime output files.
